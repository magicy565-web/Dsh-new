# Notification code closure and trust boundary

Follow-up to unified backend622fbfb. This branch adds an explicitly chosen once-only first-sample notification and connects production callback dependencies to the existing verified native-login facility. The first source is an original completed monitor check, not a fabricated early seven-day summary. It has a separate original approval, one-time subscription/message/outbox, and independent enabled template configuration. No summary send, second grant, automatic opt-in or subscription reuse is introduced.

The existing summary API remains compatible when phase is omitted. Add phase:first_sample to its existing POST commands and use the separate notification-first-status GET. Existing expectedSummaryRevision/expectedSummaryHash names now refer to the selected phase's source pointer. Both coordinator instances share original Store/commands/reservations and parent modules; there is no new schedule, queue or execution engine. Original Connectors retain capabilities until an administrator explicitly reviews the new first action.

Production callbacks now come from ORIGINAL native login. Original code2session returns server-only OpenID, the existing reviewed HMAC member map resolves that identity, and the original signed login produces the original live Session. Only after those checks can the ingress privately register that AppID/OpenID against its original Session id. Public projections expose an opaque binding id/revision/AppID, never OpenID/token/session key. Expiry/revocation/restart clears live resolution until another genuine native login. Browser sessions/header claims and client OpenID input cannot register such a binding. No user/account/role is created.

A server challenge binds the verified Session, owner/monitor, selected phase, AppID/template and one-use expiry. The server validates the existing native identity and reports decision with authorityLevel:authenticated_client_report and platformAuthorization:unverified_until_send. The popup response itself is not a signed WeChat server authorization credential. A dishonest authenticated user can misreport a popup result; the system does not independently prove that consent/counter state and the actual send API is the final enforcer. Existing original separate approval is still necessary, refusal/unknown are kept accurately, and there is no automatic re-subscription or resend. No invented certificate or new credential is used to disguise this limit.

The default native bridge and original access Session read methods are host-private. Fresh existing token snapshots are read only from a selected absolute bounded private file, with exact AppID and expiry validated by the original adapter. No access-token exchange/mint/refresh, OAuth setup, app/template registration, paid service or production call is performed. WORKSPACE_SUPPLIER_NOTIFICATION_CONFIG_FILE optionally loads existing reviewed adapter settings and token file references at original createApp/startup. Mode is forced production; firstSampleWechat is absent/disabled by default. Direct trusted dependency injection remains available for existing facilities/tests.
