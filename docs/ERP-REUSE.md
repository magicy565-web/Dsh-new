# ERP 后台设计与已有资产复用

用户要求 ERP 对标 Shopify Admin 式的经营后台。这里借鉴以商品、客户、订单和库存组织经营工作的方式，不表示接入 Shopify，也不复制其全部功能。微刊仍通过对话创建；ERP 的经营者后台是另一种使用需求。

## 已核对的仓库资产

| 实现 | 已有能力 | 处理方向 |
| --- | --- | --- |
| dsh-workspace-library 的产品部分 | 产品、多个 SKU、规格、MOQ、交期、阶梯报价、供货条件、图片、确切资料版本关联 | 作为 ERP 商品能力的复用基础，不再扩展另一份独立商品资料模型 |
| 同一插件的企业资料部分 | 原始附件、文件／文字版本、SHA、证书日期、绑定版本的审核、引用读取 | 保留为 ERP 的资料与媒体能力；统一后台入口，保持文件来源和版本标识 |
| dsh-mini-erp | 交易单价快照、供货名额、预留／确认订单、事务、到期释放和幂等 | 保留作为交易核心；每条交易 product 对应明确绑定的原 product.id + sku.id |
| packages/domain-product-library | 注入式 Medusa 上下文固定、资料页面／评论／审核和只读来源适配 | 尚无真实 Medusa 接入；不以其旧产品房间、页面和评论模型重建 ERP。必要时提取来源适配思路 |

已具备的图片上传、列表／详情／编辑页及表单逻辑可以复用，但现有资料库页面不是完整 ERP 后台。

## 商品模型及数据归属

目标是一套商品主数据：Product 描述商品，Variant/SKU 描述规格、销售单位和交易标识；订单引用 SKU，订单价格继续保留当时快照。产品详情下关联媒体、资料、供货条件和相关交易。

当前原生资料库为 profile 级 JSON 存储，ERP 是按 workspace 分区的 SQLite 账本。不能直接按名称或 SKU 文本默认为同一商品，也不能把 profile 全部资料自动暴露给任意工作区。现已使用显式 link_sku 建立 product.id + sku.id 与工作区交易标识的映射；同一原库 SKU 只能绑定一份 ERP 分配。旧账本关联要求原标识、当前修订和不变数量，不自动迁移。原库 SKU 身份必须唯一。

交易库存、订单、名额仍以 ERP 为准；资料、图片和证书保留原始附件及不可变版本标识。统一后台不要求复制附件字节或把旧报价默认升级为当前交易价格。ERP 按下单数量取原库阶梯单价，并检查 MOQ 和商品修订；缺价或价格格式不支持时需重新报价，不能按零元下单。订单保存成交时单价。

库的临时文件＋rename 与修订检查可用于资料保存，但不能代替 SQLite 的跨连接库存／名额事务。旧资料库的单企业管理员边界也不能直接声称支持多商家或公开买手登录。

## 首期后台入口

- 商品：产品列表、详情、SKU、图片、供货条件及关联资料。
- 买手：登记、列表与联系方式详情，可直接为该买手创建采购预留。
- 订单：预留、确认、取消记录及商品价格快照。
- 供应名额：区域／渠道／期限、可用量及关联预留。
- 资料：企业文件、证书、规格和媒体，可从商品详情进入。

Agent 工具与后台调用同一个服务，避免页面和 Agent 分别维护状态。微刊只读取选中内容，交易动作由 ERP 完成。

现已提供 DSH 原生 ERP 侧栏入口，商品列表／SKU 详情、关联与数量更新、订单确认／取消；商品创建／编辑现以同一个原库编辑组件嵌入 ERP，采用主辅双栏布局；资料与媒体仍可进入原资料库。未重做商品 CRUD。买手登记与预留创建已补齐后台表单，继续调用同一个 Agent 服务；权益登记仍使用原生工具。订单表单读取原库实时报价与对应商品的名额，并保留同一次提交的重试凭据。

本次检查的开发 profile 中原库产品／资料和 ERP 交易均为空，没有真实记录需要迁移，也未填充演示业务数据。验证使用临时合成记录；真实浏览器检查保留空数据状态。

页面对照与验收依据见 [ERP 后台设计](ERP-ADMIN-DESIGN.md)。

这是一套单企业、可信经营者使用的后台。原库读取与编辑在同一个 Host 进程中排队，不能据此声称跨宿主同步或多商家权限隔离。付款、物流、工单接入和公开买手交易尚未实现。
