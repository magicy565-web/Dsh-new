# Workspace 插件长期开发规范

规范版本：1.0.0  
适用对象：插件作者、宿主维护者、审查者、集成负责人和发布负责人。  
配套：[文档入口](README.md) · [新人指南](DEVELOPER-GUIDE.md) · [模板](PLUGIN-TEMPLATES.md) · [准入清单](ACCEPTANCE-CHECKLIST.md)

## 1. 地位、用语与适用范围

本文件规定插件长期应满足的工程要求，不是某个提交的功能清单，也不证明现有插件全部合规。源码能力、已执行验收和待整改项必须分别记录。旧包按维护计划逐步补齐；本规范不能作为未经批准改动既有业务政策、用户数据或生产环境的理由。

- **MUST／必须**：准入要求。不满足时不得宣称该范围合规；只能缩小交付声明，或按第 2 节办理允许的例外。
- **MUST NOT／禁止**：明确禁止的做法。
- **SHOULD／应当**：通常采用；偏离时必须说明原因、替代措施和验证结果。
- **MAY／可以**：按实际需要选择，不得据此扩大权限或制造新系统。

适用范围包括 OMP 工具与 Skill 包、连接原业务权威的 Host adapter，以及外部业务平台自身的插件。纯 Skill 适用手册、版本、安全和证据要求；没有代码、持久化或外部写入的部分可在清单中说明不适用，不为形式完整新增工具、数据库或服务。

运行时受信策略、用户授权、代码安全边界和本文件的开发要求属于不同层。合并文档、安装包、启用工具、连接账号、调用付费服务、披露资料、生产部署均不是相互代替的授权。

## 2. 规范治理与责任

### 2.1 负责人

每个插件 MUST 在 README 或项目既有负责人登记处标明维护责任人／团队、问题入口和兼容范围。每次交付 MUST 明确作者、独立审查者、共享文件集成负责人和发布责任人；一人兼任的限制及补充审查方式由项目维护者确认。

并行任务 MUST 划定文件边界。共享 Host、loader、配置、锁文件及公共契约在同一整合窗口 MUST 有一个明确写入者。各开发者使用自己的批准分支；不得以“插件开发”为由覆盖其他任务的工作。

### 2.2 修订

本规范使用语义版本：新增不兼容强制要求升主版本，新增兼容要求／章节升次版本，澄清和错字修正升修订版本。提案 MUST 说明动机、适用层、对旧包的影响、兼容／迁移方式、生效条件和验证方法。涉及授权、敏感数据或供应链边界时，MUST 增加相应责任人的审查。

规范修订经项目维护者批准并合入后对约定范围生效；既有包的迁移期限需明示，不能以文档变动暗中激活功能或撤销安全门。修改示例和操作指南时，MUST 同步核实其引用的实际 loader、SDK 和包脚本。

### 2.3 例外

例外仅用于获准的工程兼容或流程暂缓，MUST 记录：条款、精确范围、原因、风险、补偿控制、批准人、负责人、开始时间、到期时间及关闭证据。例外不得无限期自动延续；到期未复核时不得继续以例外证明准入。

项目批准人不能通过例外替用户授予资料披露、付费、生产操作或新的账户权限。例外也不能取消上级安全要求、伪造验收、把来源材料升级成授权，或将恶意代码当可信插件执行。不存在合格批准人时，依赖该例外的交付保持阻塞。

## 3. 三层插件与完整业务模块

| 层 | 应承担的责任 | 不应承担的责任 |
| --- | --- | --- |
| **OMP tool＋Skill** | 使用原生 extension 注册工具；提供受支持的 schema、结果、原生 hook 和运行时手册 | 另造模型／工具循环；从模型参数创建身份或权限；复制业务数据库 |
| **Host adapter** | 将原用户、租户、会话、接收方、授权、预算、来源及原业务接口绑定成受控能力 | 把工具描述当授权；重建订单／资料／审批的第二权威；把所有任务写死为业务 DAG |
| **外部服务插件** | 按外部平台自身扩展机制实现该平台的数据、路由、事务和管理能力 | 冒充 OMP 包；将代码交付等同于该平台已部署、迁移或可用 |

Docling、ERP、商店等外部服务的连接器与该服务本身 MUST 分清；服务可用不代表原 Host 已批准向它发送数据。一个业务功能可以横跨三层，但 MUST 逐层标明责任、版本、依赖和验收证据。

**独立不等于不依赖 Host。** 受控 Host 依赖可以是正确的安全设计。以下声明 MUST 分开使用：

1. **可打包**：包内资源、依赖声明和入口可形成制品。
2. **原生可加载**：目标原 SDK 实际发现并注册 extension／Skill。
3. **可选择启禁**：目标入口依据批准配置选择功能；禁用不会偷偷留下同等调用入口。
4. **可移除工具包**：在声明支持的进程／会话边界移除包后，其他已承诺能力仍工作。
5. **完整业务模块可装卸**：上述能力加上 Host 挂载、路由／任务、界面贡献（如有）、外部依赖、数据保留和升级回退均有明确生命周期与实测。

宣称“完整业务模块插件” MUST 满足第 5 项，列出宿主依赖和剩余静态绑定，并验证宿主在模块不存在时仍按契约工作。纯工具包或纯 Skill 不必为此新增页面、后端服务或统一注册平台；它们 MUST 准确声明自己的较小边界。确为核心必需的模块可以保留强依赖，但 MUST 标为核心依赖，不能宣传为可随意卸载的可选插件。

企业上下文与 Medusa 的实际服务接口、装配和生命周期示例见 [插件后端服务接入契约](BACKEND-SERVICE-CONTRACT.md)。该文档按实现范围声明，不将所有现有插件自动视为完整模块。

## 4. 架构与模型自主性

MUST 复用项目选定的原 OMP extension、Skill loader、Session 和模型／工具循环。新增接缝先证明现有接缝不能满足需要；不得借插件交付另造 Runtime、Agent Loop、权限引擎、业务规则引擎或平行记忆系统。

工具应提供稳定、可组合的业务能力；Skill 指导模型根据用户目标选择工具、追问缺项、跳过无关动作、调整计划或停止。MUST NOT 将“先分析、再保存、再创建决策、最后执行”等经验步骤变成所有问题必经的后端 DAG。

下列约束可以留在后端，且 MUST 准确命名：

- 授权、账户／租户隔离、接收方和数据披露门。
- 预算、审批、幂等、并发控制、事务和可恢复执行状态。
- 依赖真实前置条件的业务接口，例如没有有效订单不能发货。
- 经业务负责人批准的准入政策。其理由可能是审阅政策而非安全必然；MUST 明示配置、所有者、适用范围和变更审查。

排序建议、评分启发式和营销经验 SHOULD 放在受信手册，允许模型解释偏离。既有准入政策的移除或阈值变化 MUST 有明确需求与批准，不能仅因“让模型自主”顺手删除。

## 5. 包结构与发现

新 OMP 包 SHOULD 沿用项目目录、npm scope 和工具命名惯例；既有公开名称是兼容契约，不得仅为整齐改名。包 MUST 包含准确的 package name、version、模块类型、真实入口、发行文件清单、依赖以及实际使用的 extension／Skill 声明。

项目现有原生声明是 `pi.extensions` 和 `pi.skills`；开发者 MUST 以当期 loader 为准，不能自造尚不存在的 `permissions`、`registerPlugin` 或 UI manifest API。扩展注册 MUST 使用当期原 SDK 支持的接口，例如 `pi.registerTool`。真实示例与维护位置见 [新人指南](DEVELOPER-GUIDE.md) 和 [模板](PLUGIN-TEMPLATES.md)。

- extension 注册阶段 MUST 无业务请求、付费调用、凭据扫描和隐式持久化。
- 包内相对 import MUST 留在包内。跨包依赖 MUST 明确声明，不能引用宿主仓库私有路径来冒充独立包。
- 所有声明的 Skill、入口及资源 MUST 存在并进入实际制品。
- 包不能以安装／构建 hook 偷偷下载代码、配置账号或扩大权限；必要 hook MUST 在受支持工具链和明确审查范围内。
- 默认选择配置和功能权限 MUST 分开管理。新可选插件 MUST 默认不激活，除非批准的产品配置明确将其纳入；现有默认配置按兼容计划治理，不因本条自动改变。
- 未配置原 Host 时，工具 MUST 明确返回该工具契约定义的未配置／不可用状态，或仅执行已声明的安全纯能力；不得静默切换到未授权网络服务、模型或数据源。

## 6. 可信代码、供应链与配置

原生 JavaScript 插件运行在宿主进程或受信执行环境中。**工具授权门、manifest 校验、静态 import 检查和路径白名单不是恶意代码沙箱。** 插件代码可能直接使用网络、文件或进程能力；不得宣称声明权限会自动隔离这些行为。

安装或执行第三方代码前 MUST 审查来源、版本、完整性、依赖树、许可、安装脚本以及网络／文件／进程行为。使用仓库批准的锁文件和来源，记录制品与被测源码的一致性。依赖扫描 SHOULD 纳入 CI；扫描通过不能替代人工评审或证明无漏洞。

如需运行不可信代码，MUST 先由项目批准专门的隔离设计并验证其真实边界；不能假定当前 OMP 插件机制已提供该隔离。

配置 MUST 区分：可发布默认值、部署参数、能力选择、用户授权和秘密。秘密 MUST 由已批准的安全配置来源在运行时注入，不得写入包、Skill、AGENTS、测试 fixture、日志、PR 或示例。禁止自动扫描开发者电脑以寻找可用凭据。服务目标、超时和资源上限 SHOULD 可配置，但模型不得通过任意 URL 或自报配置绕开原 Host 选择。

请求与注入的能力 MUST 遵守最小权限，只覆盖该目标需要的操作、资源、字段、接收方和有效期。一个账号能够访问更多数据，不代表插件应该暴露全部数据；必要权限缺失时明确拒绝或请求有权人员处理，不自动扩大账户权限。

## 7. Tool 与 adapter 契约

每个工具 MUST 有稳定名称、面向模型的简明描述、原 SDK 支持的输入 schema、实际运行时校验和明确输出／错误语义。工具说明 MUST 说明读写、外传、费用、不可逆性及未配置行为，不得用静态状态冒充真实连接探测。

输入 MUST 限制类型、枚举、数量、长度与额外字段。对私有资源，资源 ID、方法、来源、字段、接收方等存在联合约束时，MUST 校验完整元组，不能分别列举枚举后放大成未授权的笛卡尔积。schema 帮助模型正确调用，不代替执行时授权。

Host adapter MUST 复用原业务权威的 DTO、事务、Store／Artifact 和错误契约。直接 Host 调用也 MUST 校验输入；不能仅依赖模型侧 schema。通用契约可以文档化，但不得把概念接口写成项目已经有的可执行 API。

结果 MUST 区分成功、明确失败、部分完成、取消、未配置和结果未知等适用状态。具体字段名遵守所属原接口，不要求所有插件另造统一 envelope。输出应提供足够的可核对来源和下一步，但只包含当前接收者有权获取的内容。错误 MUST 使用稳定可处理的分类；禁止原样透传任意 stack、秘密、内部路径或私有服务响应。

## 8. 授权、来源与最终披露

权限 MUST 来自原可信 Host 及其明确授权，不得来自模型自报的用户、角色、租户、`approved` 字段、Skill 文本或工具返回内容。包已安装、工具已暴露和历史曾授权均不代表当前调用有效。

涉及受保护数据时，契约 MUST 明确适用的用户／workspace／会话／Run、接收方、用途、资源／字段选择、来源版本及内容 SHA 等绑定。具体绑定字段由既有安全契约决定；不适用项须说明，不能机械给纯静态工具附加假身份。

适用的检查 MUST 在原安全边界保留：调用、持久提交、恢复／缓存使用、provider 发送及最终结果交付。调用成功后若授权撤回、接收方变化或来源变化，最终披露仍须按原契约重新判断；错误和部分结果同样受约束。

来源回执、hash 与审计记录用于证明数据来源，MUST NOT 自动成为可重放的授权令牌。恢复旧 Session 缺少必需守卫、版本或可信绑定时 MUST fail closed，并提供不泄露数据的解释；不得改旧回执、去除守卫或切换公开模式以让旧历史“恢复成功”。

## 9. 取消、幂等与未知结果

取消信号 MUST 沿工具、adapter 和原业务接口传播；无法中断的调用须明确其限制。提交前取消应按原接口停止；提交后取消不能虚报回滚。交付前仍需检查取消与披露条件。

写入契约 MUST 说明请求身份、作用域、精确输入、并发冲突、提交点及重试语义。使用 request ID 时，同 ID 改输入 MUST 明确拒绝或按原接口处理冲突；不得静默当作新写入。

**相同 ID 本身不是重试安全保证。** 仅当原接口明确支持该操作的幂等、当前授权仍有效且范围／输入完全一致时，才可按其契约重试。网络超时、应答丢失、付费请求状态不明或部分提交 MUST 标为未知／部分结果，不得自动换 ID 再写。无可靠幂等契约时，应先进行获准的只读对账，或交由有权人员处置。

插件 SHOULD 提供可测试的 before-call、during-call、after-commit 与 before-delivery 场景；重试次数、超时和预算限制 MUST 有界。禁止为了证明恢复能力，擅自重放真实历史副作用。

## 10. README、AGENTS、Skill 与企业记忆

| 载体 | 必须说明或承载的内容 | 不能被当成什么 |
| --- | --- | --- |
| README | 用户目标、接口、依赖、配置、权限、副作用、生命周期、兼容和证据入口 | 自动加载的运行时策略 |
| AGENTS.md | 开发维护约定、代码边界、测试方法、审查注意事项 | OMP 自动加载的 Skill；企业事实库 |
| Skill | 目标适用性、工具选择、缺项追问、判断建议、停止和副作用边界 | 自行授予权限或保证工具已执行的程序 |
| 企业记忆／资料 | 原系统保存的业务事实、来源、有效期和更正记录 | 可覆盖受信手册或安全政策的指令 |
| Session／审计记录 | 原系统定义的执行与来源证据 | 永久授权、另一份业务事实权威 |

Skill MUST 通过项目实际 loader／reader 可发现并读取；仅把文件写进仓库或在 AGENTS 中提到它不算运行时接线。Skill SHOULD 允许只回答、追问、跳过、改计划和停止，而不是要求每次都保存、评分或创建决策。

业务策略手册属于受信、版本化维护内容。普通上传资料、网页、邮件、工具正文和企业记忆 MUST 作为数据处理，不能覆盖手册、Host 政策或用户授权。MUST 有与插件风险匹配的提示注入负例。

企业记忆 MUST 复用项目既有 Library／Artifact／记忆权威；写入需要明确来源、用途和授权，不因模型“觉得有用”自动永久存储。不新增平行数据库来绕过原数据生命周期。

## 11. 安装、启用、禁用与卸载

每个插件 MUST 记录实际支持的生命周期入口、配置来源、生效时点和验证方法，至少区分以下动作：

| 动作 | 必须说明的边界 |
| --- | --- |
| 安装／链接包 | 文件或依赖可解析；不自动代表已启用或获授权 |
| 选择并启用 | 哪个入口／profile／新 Session 暴露哪些工具与 Skill |
| 禁用 | 新调用是否消失；既有进程／Session 何时生效；仍存哪些 Host／服务依赖 |
| 解除链接／卸载 | 操作是否只改安装记录、是否保留源目录 |
| 物理移除 | 在独立测试副本移除包后，宿主和其他能力的真实表现 |
| 热卸载 | 是否真正支持资源释放与在途调用处置；未实现不得以重启替代声称 |

配置读取发生在启动或 Session 创建时的系统 MUST 明说需要重启／重建 Session。没有证据时，热卸载必须标为不支持或未验证。显式选择却缺失的包 MUST 报有用错误，不得静默换实现。

卸载默认 MUST 保留业务资料、订单、Artifact、Session 和审计记录；清理缓存、删除插件私有持久数据和业务数据删除是分别的操作，须说明保留期、恢复途径及授权。禁用某个工具不代表原业务服务已停止；外部插件必须单列服务停用、路由、定时任务及数据库的处理。

## 12. 依赖、版本、兼容、迁移与回退

SDK、运行时、依赖和 peer 版本 MUST 从当期仓库批准的锁及兼容声明确认，不把某次审计版本永久写死为本规范。声明 peer 不是完成安装；实际目标环境的解析路径和打包后依赖必须验证。

以下变更 MUST 评估兼容性：工具名／schema／结果、Skill 指导、默认配置、Host 契约、权限、来源绑定、Session 持久字段、外部 API 和数据库 schema。破坏性变更 MUST 明确版本升级、受影响调用者和旧版本处置。

弃用 MUST 给出替代方式、支持窗口／停止条件、告知渠道及迁移验证。窗口根据风险和用户需求批准，不预设统一天数。不能在过渡期维持已知不安全的授权绕过。

迁移 MUST 分清代码、配置、业务数据和历史会话。是否原地迁移、重新授权或拒绝恢复由原系统契约决定；不得把旧包或旧引擎历史自动转换成新权限。回退 MUST 包括兼容代码／配置、数据前后向兼容、已提交副作用核对及停止条件。代码降级不等于数据回滚；无法安全回滚时须准备前向修复或人工恢复。

历史兼容运行路线仅是经验证的兼容选项；主运行时失败时，MUST NOT 未经批准自动切换运行时、模型、接收方或权限范围。

## 13. 日志、数据生命周期与运维

日志 SHOULD 记录可关联的请求／操作 ID、版本、状态和必要原因，但 MUST 脱敏并最小化。秘密、完整私有资料、模型原始上下文和业务运行数据库不得作为普通源码 fixture 或 PR 附件。

持久化数据 MUST 有权威存储、归属、保留期／规则、访问边界和删除责任人。缓存 MUST 说明失效条件及源变更／撤权的处理，不得以缓存绕过最新授权。对外传输 MUST 明确接收系统、字段、用途与批准范围。

网络、文件、并发、时间、大小、费用与重试 MUST 按功能风险设置有界限制；具体额度由当次运行／部署的批准配置决定，不由本文永久指定。未知费用或未知提交结果应计入风险并停止不安全继续。

## 14. 测试分层与证据口径

每次交付 MUST 提供适用测试矩阵、精确命令、被测源码／制品版本、原锁环境、替身范围、退出状态和未跑原因。状态至少区分通过、失败、跳过、未执行和不适用；后两项不得计作通过。

| 层 | 证明范围 | 不能单独证明 |
| --- | --- | --- |
| S 静态 | manifest、语法、路径、资源、依赖声明、代码审查 | 实际加载、业务执行、安全隔离 |
| P 纯／契约 | 纯函数、DTO、schema、错误及合成接口 | 真实 SDK／Host／外部服务 |
| H 原 Host＋合成依赖 | 原授权／事务接缝及指定替身条件 | 真实外部系统和真实模型 |
| K 原 SDK | 目标版本真实发现、注册、Skill 与 Session 行为 | 真实账号、业务数据或模型质量 |
| E 真实服务 | 指定服务／测试租户的真实边界 | 模型自主选择或完整用户流程 |
| M 真实模型 | 指定模型条件下的自主调用／追问行为 | 所有模型、所有用户与全部异常路径 |
| U 用户流程 | 指定环境、身份和场景的端到端体验 | 未覆盖版本或未列场景 |

以上分类可以组合，不能拼接不同版本和环境的局部结果冒充同一链路通过。作者、独审和集成环境的证据 MUST 各自注明版本；替代依赖、转译适配或模拟 SDK 的结果不得标为原锁 SDK 验收。

基础 CI SHOULD 默认无凭据、合成数据、无真实业务副作用；必须在记录中说明仍可能发生的依赖下载等网络行为。可用时 SHOULD 限制非必要网络。真实服务、模型、支付或生产验证 MUST 另有明确范围、接收方、预算和停止条件，不得由普通测试脚本隐式触发。

至少根据风险覆盖：未配置、缺依赖、非法输入、越权、来源变化、撤权、取消、并发、幂等冲突、未知结果、错误泄露、提示注入、禁用／移除和受保护历史拒绝。完整模块声明还需完整 Host 无模块启动与其他功能回归。

项目根测试命令不自动代表全部插件；MUST 查阅当期脚本实际枚举范围，补上包内与专用 runner。测试集合数量 SHOULD 由真实发现结果维护，新增包不得通过删包、跳过失败或伪造计数凑绿。

## 15. 集成、发布与持续维护

交付 MUST 包含：源码／制品版本、影响范围、契约与兼容说明、清单、独审结论、证据和未验项、配置／迁移步骤、回退方案与负责人。MUST 核对最终集成版本的变更和远端状态；源分支通过不等于整合后自动通过。

独审 SHOULD 覆盖代码边界、可信代码风险、权限／披露、状态与重试、生命周期和证据质量；高风险接口不得仅由实现者自证。无法跑适用验证时，可以提交受限范围的代码或文档审查，但 MUST 明示阻塞，不能称生产就绪。

开发分支、PR、合并、发布制品、生产部署、数据库迁移、连接账号与激活功能 MUST 按项目受保护分支和批准发布流程分别核准与执行。既有开发授权不隐含受保护分支合并、强推、生产部署、付费、创建凭据或扩大权限；每次操作以当时有效授权为准。

发布后维护计划 SHOULD 包含监控信号、问题入口、依赖更新、兼容矩阵和弃用跟踪。收到安全问题或未知写入时，优先保全最小证据、限制进一步副作用并按原流程处理；不得为恢复“可用”绕开授权或隐藏失败。

## 16. 合规声明

插件 README／PR MUST 说明：适用规范版本、符合的层级、例外、未验证项和可声明的生命周期范围。可使用 [准入清单](ACCEPTANCE-CHECKLIST.md) 记录。

“遵守本规范”不等于“所有现有插件已验收”，也不等于“可以执行任何用户任务”。判断始终基于当期源码、当前有效授权和可追溯的实测证据。
