# Supplier service v1 — stable client contract

The existing original conversation is the entry. Backend development owns this contract; the mini-program thread continues its procurement wiring independently. No new UI, marketplace, task scheduler or credential is required.

`/api/conversations/:cid/supplier-services` is an owner-scoped collection. Always encode the opaque conversation ID once. GET returns `{services}`. POST `{requestId, content}` admits an original Pi run and returns 202 `{serviceId, revision, run}`. GET `/:sid` returns `{service}`. POST `/:sid/messages` `{requestId, expectedRevision, content}` clarifies through the same Pi/pi-durable runtime. POST `/:sid/profile` `{requestId, expectedRevision, facts}` persists explicit structured user facts without a model call. All unknown values remain null; image arrays start empty. Retain the exact requestId/body after an uncertain response.

Facts: `name`, `description`, `targetMarket` (ISO country code), `currency`, `skuCode`, `supplierUnit`, `supplierMoq`, `wholesaleUnitPrice`, `wholesaleCurrency`, `internalUnitCost`, `internalCostCurrency`, `recommendedRetailPrice`, `retailUnit`, `unitsPerPack`, `consumerPrice`, `productionDays`, `handlingDays`, `shippingDays`, `images`. Money uses decimal strings and explicit currency. MOQ and production time do not become pack quantity or shipping time. Recommended price does not become consumer price. Images use original `{kind:'artifact',asset:{artifactId,version,sha256},sourceNote}` or `{kind:'public_url',url,sourceNote}`; remote availability remains unknown without an authorized observation.

POST `/:sid/preview` `{requestId, expectedRevision, confirmed:true, publicFields}` returns `{service,preview}`. Public fields allowed: name, description, skuCode, retailUnit, unitsPerPack, consumerPrice, handlingDays, shippingDays, images. Wholesale/MOQ/cost/recommended price/production remain private. Preview includes real `product.descriptionHtml`, `variants`, `saleUnit`, `market`, `fulfillment`, `images`, `display`, missing fields and a content hash. `externalStatus:'preview'` is never a Shopify draft or publication receipt. Shopify writes require a separate host configuration and exact human approval; they remain off during this development.

GET detail returns `{service}` with `id/serviceId`, `conversationId`, integer `revision`, `phase` (pending/needs_information/preview_ready/blocked/failed/interrupted/cancelled/rejected), `profile`, `profileHash`, `missingFields`, `{field,question}[] questions`, unconfirmed `suggestions`, original `runId/error`, `preview` or null, private `productReference` or null, `externalStatus` and `external` or null. Editing facts increments revision and clears preview. Preview returns both `previewHash` and `contentHash` (same canonical content digest); its revision is the post-confirmation service revision. Invalid image bytes/version/hash are unavailable, remote URLs remain unknown. GET `/:sid/images/:index` uses the same authenticated owner and original exact file/SHA bytes.

POST `/:sid/save-product` `{requestId,expectedRevision,confirmed:true}` saves known facts through the original library API and its durable receipts, returning `{service,product}`. Supplier MOQ/wholesale tiers/production lead time retain their original library meaning; private commerce fields remain in the owner-scoped service record. A lost library save resumes its original receipt, without creating another product.

POST `/:sid/shopify-draft` `{requestId,expectedRevision,expectedPreviewHash,confirmed:true}` currently returns `status:'blocked'`, code SHOPIFY_SETUP_REQUIRED or SHOPIFY_PRODUCT_WRITE_NOT_AUTHORIZED. No write grant is installed or inferred. POST `/:sid/shopify-observation` `{requestId,expectedRevision,shopifyProductId,publicationId?,confirmed:true}` reads an existing product through the reviewed original store and product scope; successful observation yields exact shop/product/variant IDs and `shopify_draft/unpublished/published` according to actual status/publication. ACTIVE alone is not published; UNLISTED may be published with direct-link-only visibility. Observation has relation user_selected_existing_product, evidenceKind shopify_admin_read and writeReceipt null; it never claims this preview was created or published remotely. Other-channel observation cannot supply the online-store publication start date. Creating or publishing a remote product is not enabled in this milestone.

POST `/:sid/monitors` `{requestId,expectedRevision,shopifyProductId,variantIds?,startAt?,startFromPublication?,confirmed:true}` configures exactly seven days. Specify a UTC timestamp or explicitly select a verified online-store publication timestamp, never both. Return `{monitor,service,activation:'disabled_requires_original_schedule_approval',status,error}`; without shop configuration status is blocked. Monitor DTO has immutable `scope`, `scopeHash`, original `goalId/scheduleId`, `status`, `scheduleEnabled`, `checks`, `latestSample`, `summary`, metric definitions and `externalNotifications:'not_configured'`. GET `/:sid/monitors` returns `{monitors}`. Original Schedule approval/enable is separate; configuration never enables it or establishes external monitoring. The original Schedule facility invokes a deterministic registered service handler, with original claim/revision/hash checks and zero model calls.

POST `/:sid/monitor-check` `{requestId,monitorId,expectedMonitorHash,confirmed:true}` explicitly reads the original cohort and returns `{monitorId,sample,summary}`; exact request replay returns its durable result without another API read. Sample has `salesStatus` available/unavailable, `trafficStatus` available/partial/unavailable/unsupported, nullable `sales/traffic`, `sampledAt`, `{from,to} coverage`, `dataLagSeconds:null` when unknown, completeness and source error codes. Complete empty acknowledged order cohorts can be zero; authorization/network/truncated pagination cannot. Product/variant counts exclude test orders, retain cancellation/refund overlap and use currentQuantity for retained units without subtracting refunds twice. Order-level revenue is not mislabeled product revenue. Product traffic requires an existing reviewed exact-product adapter; ShopifyQL whole-store sessions are not substituted.

GET `/:sid/monitor-summary/:monitorId` returns `{summary}` or null. End summary has a stable messageId/notificationCount=1 in the original conversation, scope window and contentHash/revision. Later data can correct that same summary, never add another final notification. No external delivery is configured or claimed. POST `/:sid/monitor-stop` `{requestId,monitorId,expectedMonitorHash,confirmed:true}` stops the original schedule and monitor.

Official references checked 2026-10-12: [productCreate](https://shopify.dev/docs/api/admin-graphql/2026-10/mutations/productCreate), [publishablePublish](https://shopify.dev/docs/api/admin-graphql/2026-10/mutations/publishablePublish), [ShopifyQL Admin API](https://shopify.dev/docs/apps/build/shopifyql/graphql-admin-api), [sessions schema](https://shopify.dev/docs/api/shopifyql/latest/schemas/sessions_and_behavior/sessions), [LineItem](https://shopify.dev/docs/api/admin-graphql/2026-10/objects/LineItem), [RefundLineItem](https://shopify.dev/docs/api/admin-graphql/2026-10/objects/RefundLineItem). ProductCreate is unpublished; channel publication is distinct and requires active product status plus write_publications. ShopifyQL requires read_reports and protected customer data Level 2; it is not real time. The examined sessions schema does not supply product attribution; this service will not reuse whole-store sessions as product traffic or request additional permissions automatically.

## Cancellation, browser preview and existing MCP adapters

POST `/:sid/cancel` or `/:sid/reject` `{requestId,expectedRevision,expectedProfileHash,confirmed:true}` retains facts/history, invalidates preview, cancels only its own active original Pi run and prevents further editing or recovering that intake. Exact retry does not repeat the state change. A different conversation run is never cancelled. Original Muse files use their owner Session download protocol. GET `/:sid/preview-page` renders this authenticated confirmed preview as a standalone HTML card; it is not a replacement main UI or a claim of mini-client integration.

`WORKSPACE_SUPPLIER_MCP_ENABLED` defaults false. Opt-in exposes two read tools over the existing Dot `/mcp` or exact original Muse `/api/muse-worker/mcp` credentials/Host/owner: `workspace_supplier_listing_preview` and `workspace_supplier_monitor_status`, arguments `{taskRef,attemptId,fence}`. Muse facet exposes only these two reads; claim/mutations stay on original REST. Default Dot eleven tools and original Muse protocol remain unchanged. Original task approval, ownership, active lease and cancellation are checked. A token alone grants no supplier data. Private image IDs/bytes and supplier price/cost fields are omitted.

POST `/:sid/task-scope` `{requestId,expectedRevision,expectedPreviewHash,confirmed:true,monitorId?,expectedMonitorHash?,shareCurrentMetrics?}` emits inert `{publicProductText,originalTaskApprovalRequired:true,executionStarted:false}`. It does not create or approve an order. The original separately approved public task must contain that exact scope in inputs.product. Current aggregate metrics require a separate explicit share flag and exact monitor hash. Changed preview, stopped intake, expired/revoked task lease or removed approving member block reads.

`createSupplierOwnerMcpBinding` exports closed get/intake/profile/preview/monitors/monitor_check callbacks for the original owner custom Connector. Original trusted Host supplies its existing actor and a fresh reviewed resource scope on every call; Pi intake additionally needs that scope's explicit approval. No credential or grant is created, and no binding is installed automatically. Real unavailable Host/Muse remains an integration blocker; a normal model API never substitutes for Muse.
