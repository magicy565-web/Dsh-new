# Seven-day external notification adapter — host wiring contract

Base: `08a760c045474ed92244bf2ac01e883d91a0a17d` (PR45). This additive module does not install an HTTP route, change `server/index.mjs`, alter the original Schedule, or configure a credential. The parent task owns wiring. Default is `blocked / NOTIFICATION_UNCONFIGURED`.

## Minimal interface

`createSevenDayNotifications({store, adapter, resolveRecipient, subscriptions, authorize, clock})` uses the original Store and attaches **one** `externalNotification` receipt to an existing supplier monitor. It does not create a queue, task, timer, scheduler, or separate persistence system. The existing business notification is `monitor.summary.messageId`; its contentHash/revision remain owned by Supplier Monitoring.

The authenticated original host calls `forActor(actor, {command})`. `command` is the existing supplier command receipt function supplied by the parent service, with its original `(state, actor, serviceId, action, body, work)` signature. Methods:

- `configure(cid, sid, {requestId, monitorId, expectedMonitorHash, recipientBindingId, expectedBindingRevision, subscriptionId, confirmed:true})`: bind one exact recipient and one subscription receipt. Configuration is inert; it does not send.
- `dispatch(cid, sid, {requestId, monitorId, expectedMonitorHash, expectedSummaryRevision, expectedSummaryHash, confirmed:true}, {signal?})`: one explicitly authorized invocation by the original task/owner. Recheck the owner, current summary, binding, cancellation and subscription before network handoff.
- `cancel(cid, sid, {requestId, monitorId, expectedMonitorHash, confirmed:true})`: stops a pending handoff. Once handoff occurred, retain the actual platform result or unknown outcome; cancellation cannot recall a WeChat message.
- `get(cid, sid, monitorId)`: minimized delivery projection; never returns OpenID, access token, template payload or subscription proof.
- `recover()`: original host startup only, with no other instance actively dispatching. A persisted handoff becomes `unknown`; preparation interrupted before handoff becomes blocked. Neither is automatically sent.

`adapter` is a trusted server dependency: `{channel, fingerprint, status(), validateRecipient(recipient), validateSubscription(grant, {recipient, monitor, now}), recipientFingerprint(recipient), send({recipient, subscription, summary, signal, beforeSend})}`. Validators and the fingerprint function are synchronous; return true only for that channel's exact identity/authorization evidence, and a SHA256 digest of its private identity. `status()` returns `{status:'configured'|'blocked', evidenceKind}`. `send` returns `{status, code, providerCode?, classification?, subscriptionRevoked?, evidenceKind}` and must await `beforeSend()` exactly once immediately before its sole provider POST. No retry, redirect, fallback, receipt fabrication or unreviewed callback is allowed. Email can implement this same interface later with its own identity/consent validators; no vendor is selected.

`authorize(state, {actor, monitor, operation:'external_notification'})` synchronously rechecks the original current member/owner/task and the explicit external-send approval in the original Store, returning true only for that exact authorized action. It is checked during configuration, admission and immediately before handoff. An absent callback keeps the service blocked. The read-only monitor's Schedule approval is insufficient.

`resolveRecipient({actor, recipientBindingId})` must freshly resolve an existing reviewed server binding, never a client OpenID/subject. It returns `{id, revision, workspaceId, ownerSubject, recipientSubject, verified:true, appId, openid, revoked:false}`. Initial implementation permits only the authenticated owner as recipient; sending to another person requires separate explicit sharing authorization and implementation. Binding revision is pinned; a changed or revoked binding blocks handoff. This does not register accounts or alter permissions.

`subscriptions` is a synchronous transactional port into the **existing** host subscription/authorization records: `read(state, {recipient, subscriptionId, monitor})`, `reserve(state, {subscriptionId, deliveryKey, attemptId})`, `settle(state, {subscriptionId, deliveryKey, attemptId, outcome})`. All reservation/settlement writes occur in the original Store transaction. Reserve must atomically reject a used/reserved one-time grant, including use by another monitor/channel, and return `{reserved:true}` only on success; settle must be idempotent by deliveryKey/attemptId and never restore a grant after handoff. Read returns `{id,channel,kind:'one_time',state:'available',decision:'accept',proofId,workspaceId,subject,recipientBindingId,bindingRevision,monitorId,scopeHash,summaryId,acceptedAt,expiresAt?,...channelEvidence}`. WeChat channelEvidence is `{appId,templateId,source:'wx.requestSubscribeMessage',provenance:'authenticated_wechat_client',evidenceKind:'wechat_client_subscription'}`. No callable port means blocked. Do not add an independent grant database just to satisfy this interface.

On `outcome.subscriptionRevoked:true`, the original authorization facility must invalidate active evidence for that recipient/AppID/template, as well as the attempted grant. Explicit user revocation must immediately affect `read` and stop pending original task handoffs; the parent supplies cancellation/abort linkage. A fresh real opt-in cannot cause a cancelled/attempted summary to be pushed again. Persisted grant reservation is retained for unknown results.

Subscription evidence is a server-bound receipt of an authenticated WeChat client's fresh `wx.requestSubscribeMessage` result for this exact AppID/template/recipient/monitor. Require `decision:'accept'`, `source:'wx.requestSubscribeMessage'`, `provenance:'authenticated_wechat_client'`, exact IDs/revisions, timestamp and proofId; saved preference settings, generic schedule approval and `errMsg:ok` alone are insufficient. A client callback is not a signed server delivery receipt: the host must bind it to the original authenticated login and single-use server challenge, and the WeChat send response still enforces real platform authorization. Fixtures cannot supply production authority. Revocation makes `read` return revoked immediately. Binding/authorization ports are necessary production integration work; this PR creates no credentials or subscriptions.

## Delivery semantics

The stable local deliveryKey includes workspace/owner/monitor scope, summary messageId, channel and recipient binding; it excludes summary revision, requestId and template configuration. One external notification per monitor is retained. Corrections before handoff must be explicitly re-reviewed; corrections after handoff update `latestSummary` without changing `submittedSummary` or making another POST. Rebinding/configuration after a handoff is forbidden. Cancellation is terminal for this notification.

`platform_accepted` means an acknowledged WeChat success response, not device delivery, read status or business acceptance. All projections independently return `userRead:'unknown'`, `businessAcceptance:'not_recorded'`; the original control journal acknowledgement does not establish either. Local fixture success is marked `evidenceKind:'local_fixture'` and cannot claim real WeChat receipt.

Transport timeout, connection loss, invalid/truncated/oversized response, HTTP error/redirect, ambiguous platform result and crash after handoff mean `unknown`, `automaticRetry:false`, `reconciliationRequired:true`. The send API has no application deliveryKey parameter or query-by-key guarantee; we make no exactly-once external-delivery claim. Known platform rejection is `failed` with a bounded numeric code and classification; no raw error text/URL/token is retained. A 43101 refusal blocks subsequent subscription use; automatic re-subscription is prohibited. Unknown results must remain unknown unless a separately reviewed official reconciliation capability supplies proof. No resend method is exposed here.

## Production minimum

Parent wiring must preserve original owner/monitor/task/schedule approval checks and call this module only from an explicitly authorized notification action. Existing schedule approval for a read-only monitor does not authorize external communication. Required: reviewed AppID, an eligible enabled once-only template and field mapping, existing server-managed access-token provider for that same AppID, explicit enable flag, private exact recipient binding, fresh real client subscription receipt, durable transactional subscription port, parent cancellation/revocation linkage, and production outbound policy approval. Default remains blocked until each exists. Do not acquire permissions, tokens, credentials, deployments, paid services or recipient consent automatically. Independent security review remains a separate blocked gate; this business implementation does not replace or retry it.

In the parent supplier service's existing `forActor` closure, attach a separate `notifications` facade with `notifications.forActor(actor, {command})`; do not overwrite the supplier service's `get` method. Parent startup calls `recover()` before enabling any existing task dispatch. The parent can later expose explicit owner-scoped notification routes and register the invocation in the original task handler after its external-send approval check; this PR does neither. The existing monitor DTO still reports `externalNotifications:'not_configured'` until parent wiring deliberately changes its projection, and no integrated production delivery should be advertised from this PR alone.

WeChat adapter configuration is supplied directly to `createWechatSubscriptionAdapter`: `enabled:false` by default, AppID, templateId, `fields` mapping (1–3 `thingN`/`phraseN`/`dateN` keys to `title`/`status`/`endDate`), optional static in-app page path without query strings, miniprogramState, getAccessToken, and `officialContractReviewed:true` only after current official server-contract verification. Token provider returns `{appId,accessToken,expiresAt}` internally using existing approved credentials; the module never obtains one itself. Mapping is copied/pinned. The notification sends only a fixed title, completion/data-quality state and end date. Details and corrected metrics remain in the authenticated original summary. Fixture mode requires an injected local transport and accepts only `local_fixture` subscription evidence; production refuses fixture authority.
