# Pre-service market references and seven-day sales standard — package 0.3.0

The service standard is set before actual service starts. A historical 7/28/90-day source window informs a proposed future 168-hour sales target; it is not the service execution clock. This is an additive adaptation of existing market plan/artifact/Skill and market assessment code, with no new tool, MCP gateway, collector, vendor plugin, execution framework, approval system or shared Host wiring.

## Original interfaces

`workspace_market_validation_product` reads the existing authorized uploaded product; `workspace_market_validation_plan_save` accepts optional per-path `marketReferences` and `serviceTarget` within its existing plan input. Existing version-1 plans remain valid. A singular `marketReference` shorthand is accepted, but cannot coexist with the collection. A service target is optional: asking questions or saving incomplete/reference-only drafts remains possible. Both ordinary package loading and absent real Host bindings stay unconfigured. New targets explicitly measure `net_paid_units`, not a default conversion rate; legacy explicitly selected market comparison metrics remain separate.

Each normalized reference contains a unique ID; `sourcePlatform` (`tiktok`, `amazon`, `other`); source channel namespace; provider/tool/schema URL (explicit null with a documentation gap if unknown); evidence reference and snapshot SHA; observation timestamp; region, leaf category, use case, currency/price band; uploaded factory product ID/revision; product-vs-listing/variant sales scope; reported/estimated status, explicit salesUnit (units/orders/packs/unknown) and its definition; a dated historical period; selection, exclusions, zero-sale coverage, unknown population count and limitations; and bounded comparable rows with product IDs or ASINs. This is our normalised input contract, **not a claimed native FastMoss or Sorftime schema**. Vendor mappings/version/parent-child scope remain unknown until safe integration supplies them.

FastMoss/TikTok and Sorftime/Amazon coexist as independent references. No cross-platform pooling, implicit currency conversion or ASIN-parent aggregation exists. The target chooses one explicit referenceId. Each reference gets a separate unweighted arithmetic sample mean, median, sample/measured/missing counts and min/max range. Missing values stay null; zero sales stay in the sample. Duplicate IDs, mismatched region/leaf category/use/price and mixed estimated/reported definitions are rejected. Bestsellers-only, unknown/omitted zero-sale coverage, incomplete samples and fewer than two observations cannot directly produce a reference-derived standard. Orders, packs or unknown units remain independently reported and cannot silently become a product-unit service target. Samples below ten retain an explicit small-sample warning; no unsupported population mean or statistical confidence interval is asserted.

The seven-day reference is `sampleMean × 7 / historicalDays`, with source days, method, median/range and seasonal/new-product differences retained. It is a linear historical rate, not a forecast. A proposed target is `round(sevenDayMean × adjustmentBasisPoints / 10000)`, bounded by user-reported unverified supply, with price in the selected comparable band/currency and explicit original proposed budget. Pricing, budget, supply, seasonality, new-product, sales-definition and cross-channel rationales are required; budgets remain unapproved/unspent. Original source product matching is a draft Agent judgment, not independent classification certification.

## Human confirmation and immutable standard

The original plan tool recomputes `preServiceReview` into the existing artifact and saved receipt. Source verification remains `external_claim_not_independently_verified`; data in model-written drafts does not become verified by saving or human agreement about a service standard. It saves no human approval, schedule, launch or paid operation.

The existing trusted acquisition receipt reader receives the artifact ID/version/SHA/planHash and the derived review. For a new service target it must resolve an original **prelaunch human confirmation record** as `serviceTargetConfirmation` with exactly: status=approved, evidenceKind=real, approvalId, evidenceRef, approvedBy, workspaceId, approvedAt, planId, planRevision, planHash, targetHash, referenceHash and reviewHash. It must match the owning member/workspace and immutable plan, and follow artifact creation and historical data availability while preceding actual acquisition start. Review hashes bind the selected source summary and proposed target. No plan/tool input can submit confirmed/approved or this proof. Original monitor/schedule approval is not substituted for customer confirmation of the service standard.

The reader creates a versioned `workspace.confirmed-service-target.v1` snapshot. The original monitor freezes this into its existing scope/hash. New valid targets with the same save requestId are rejected as changed requests; new request IDs create separate unreviewed artifacts. Changed artifact versions/hashes, evidence, target, confirmation or post-start standards are refused. Full source rows remain in the original plan artifact; the monitoring snapshot retains summary/IDs/hashes and confirmation references. Original artifact/input/Goal size limits remain unchanged; do not expand permissions or storage limits for large vendor results.

This task implements the confirmation **reader contract**, not a new confirmation UI or a fabricated human decision. The real acquisition/confirmation resolver is still absent by default. Integration must bind it to the existing reviewed original human records; no production start is claimed.

## Two independent end-of-service answers

With a confirmed service target, assessment status/evaluationBasis describes attainment of that preconfirmed sales standard; `serviceTargetAssessment` repeats that explicit result and `marketComparison` reports the independent original strict market comparison. A service pass requires a real net-paid order, sufficient net-paid units for 70% of the agreed target, complete zero-lag 168-hour coverage and every original required measurement. Missing evidence or inconsistent counts cannot pass. Goal verification remains false and the original Goal remains for human review.

Example is synthetic: TikTok comparable sample mean 400 units over 28 days gives a 100-unit seven-day historical reference. A human may confirm an explicitly adjusted Shopify service target of 50 units after reviewing budget/price/supply/channel/new-product differences. One verified paid order with 35 net paid units meets 70% of that **50-unit service target**. It does not meet or prove 70% of the TikTok market mean. `marketMeanAttainmentInferred=false`; direct market comparison still refuses mismatched TikTok/Shopify channels, definitions or missing credible benchmark. An Amazon reference remains a separate sample/window and is not averaged into TikTok.

## Public schema boundary and real gaps

The [official MCP Tools specification](https://modelcontextprotocol.io/specification/2025-06-18/server/tools) describes tool input/output schemas and server-produced structuredContent alongside text content. We use this only as a public result/schema boundary; no MCP transport or authenticated data call is implemented. FastMoss's public [developer entry](https://developers.fastmoss.com/home) was indexed, but public documentation page retrieval timed out in this environment; no native response-field mapping is claimed. Per the latest delegation, further FastMoss/Sorftime schema research is owned by the parent thread; unknown fields and quotas remain gaps.

No chat key is read, copied, configured or invoked. There is no purchase, free-trial rotation or assumption that quotas stack. FastMoss/Sorftime are future ordinary external data services. Actual MCP authority/recipient binding, original source snapshots, native field/period/estimate semantics and ASIN-parent scope, original customer confirmation/execution receipts, exact paid outcome and traffic/inquiry sources all remain real integration prerequisites. Synthetic source/proof tags exercise contracts and are not real data or human business acceptance.

Future external queries must use public or explicitly authorized matching criteria. Permission to read a private Library document does not authorize disclosing its contents to a data provider. Source text remains untrusted data and cannot grant permissions or override the original Host's rules.

## PR81 integration points

No Shopify product files or shared Host wiring are changed here. The reference match binds the original uploaded factory product UUID/revision. PR81 must preserve its product/SKU-to-Shopify product/variant mapping in the original reviewed acquisition/execution receipt. A target currently measures all-product net-paid units; source ASIN single-listing/variant counts must retain their own sales scope and explanation and must not be silently summed into a multi-variant product reference. Representative price choice belongs in the matching rationale. A future per-SKU service standard needs an explicitly versioned scope and user confirmation, not an implicit allocation across PR81 variants. ExecutionChannelId must equal the original receipt's real execution channel; sourcePlatform/channel remains independently recorded.
