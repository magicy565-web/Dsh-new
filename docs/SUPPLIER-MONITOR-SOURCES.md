# Existing-source traffic and notification contracts

This later development round has not activated analytics or external notifications. The original supplier monitor and original schedules remain the only monitoring machinery. Missing source data is null/unsupported/unavailable, never an invented zero. Local fixture checks prove contract behavior only.

## Product traffic

The existing injectable host adapter contract in `server/supplier-monitoring.mjs` requires an already reviewed authorization, a stable adapter ID, `productAttribution: exact_product_id`, and `readProductTraffic({shopId, productId, from, to, signal})`. Its response must identify the same exact shop/product, attribution, actual covered interval, measured sampledAt, complete flag and nonnegative integer sessions; measured delay is nullable. Configuration alone does not establish available traffic. Adapter identity is frozen in the original monitor scope and checked at each sample. Partial/delayed coverage is visibly partial.

Official-source findings, verified 2026-10-12:

- [ShopifyQL Admin query](https://shopify.dev/docs/api/admin-graphql/2026-10/queries/shopifyqlQuery) requires existing read_reports and Level 2 protected customer-data access. This service neither requests nor installs these grants. [The sessions schema](https://shopify.dev/docs/api/shopifyql/latest/schemas/sessions_and_behavior/sessions) contains customer.storefront_event.product_viewed conditions, but this is not by itself evidence that a session aggregate is attributed to the exact product within the requested seven-day interval. No live query/response, source coverage or exact-session attribution is verified here. A whole-shop session count or lifetime customer predicate cannot be labelled product traffic.
- [Web Pixels product_viewed](https://shopify.dev/docs/api/web-pixels-api/standard-events/product_viewed) supplies event identity/time and productVariant/product identity. It counts page-view events; it is not directly a sessions metric. [App pixel setup](https://shopify.dev/docs/apps/build/marketing/build-web-pixels) requires write_pixels and read_customer_events, an installed extension and explicit activation; [pixel privacy](https://shopify.dev/docs/api/web-pixels-api/pixel-privacy) affects consent and collection coverage. No pixel is installed, activated, collected or retrospectively synthesized. A reviewed existing event source could later supply product views with its own separately agreed metric, coverage and deduplication contract. That would require an explicit metric change, not passing views into the current sessions field.

Therefore the real traffic source is presently blocked by both an unspecified supported exact-product sessions source and unverified existing source permissions/data. The existing generic host-reader code is usable; no concrete live analytics driver or sessions pipeline has been added. The seven-day order-sales reader remains implemented with original shop/product/variant scope and full bounded pagination; late cancellations/refunds can correct the original summary.

## Notifications

The implemented delivery destination remains the original conversation. Its summary has one original message identity and revision/content hash; a correction updates that summary without claiming another notification or another external send.

A future external-channel contract must freeze, on the original monitor, the original reviewed Connector ID and revision, provider/channel, authorized recipient binding (Workspace subject + provider recipient identity), consent/authorization reference where required, template/version if required, and exact summary revision/content hash. Each send needs the original explicit capability approval and original connectorRun; the deterministic business key is monitorId + summary revision + channel + recipient. A provider acknowledgement must carry a stable provider message ID and actual accepted/failed/unknown status; acknowledgement alone cannot prove that a user read or even received a notification. An unknown send outcome is reconciled on that original record without resending, unless a separately reviewed action explicitly permits a resend. No independent notifier queue or scheduler is allowed.

No WeChat template, authorized recipient/openid, email sender, messaging Connector or channel preference has been supplied/verified for this round. The concrete external-channel adapter and provider reconciliation therefore remain missing-code blockers as well as missing destination/authorization. No external send endpoint is falsely exposed as complete. Do not ask for credentials in chat; any later authorized configuration uses existing server-side reviewed references.
