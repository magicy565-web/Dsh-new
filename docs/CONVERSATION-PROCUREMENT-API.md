# Conversation procurement contract

The product entry is the original business conversation. These APIs persist references and consent in the existing Workspace Store. They do not create another execution engine, infer consent, send email, or invoke a model.

## Enterprise resources and ownership

Existing `/api/library/products`, `/api/library/documents` and `/api/conversations/:id/library-references` remain the product/enterprise resources. A supplier listing is not automatically enterprise inventory or Shopify inventory.

- `POST /api/supply/suppliers/:id/merchant`: `{requestId, expectedRevision, merchantSubject, confirmed:true}`. Admin only; subject must be an already configured enterprise merchant. Cannot change ownership while an active buyer share exists or transfer historical shares/replies to another merchant after revocation.
- `POST /api/supply/listings/:id/product`: `{requestId, expectedRevision, productId, expectedProductRevision, skuId, confirmed:true}`. Admin confirms an exact saved enterprise product/SKU. No vendor-name or SKU-text matching. Product revision changes require a fresh binding/review. Shopify operations are not required for this loop.

## Personal Agent procurement MCP

The existing `/mcp/sourcing` private transport stays disabled by default. Read-only legacy credentials keep their three publication lookup tools. A trusted Host binding `{subject, workspaceId, tokenDigest}` grants a separate buyer identity; request bodies cannot select a principal. Optional `WORKSPACE_SOURCING_MCP_PRINCIPALS_FILE` loads the reviewed array from an absolute private file. The bindings must use this exact workspace, distinct subjects from enterprise members, and credential digests different from Dot/Muse. No credential is generated by this loader. Original native Host presentation additionally requires the exact reviewed `sourcingOwnerSubject`; it retains original actor/epoch guards and awaits asynchronous resource reads.

- `workspace_procurement_draft`: `{requestId, listingId, quantity, destination, notes?}` → private `inquiry`; nothing is shared.
- `workspace_procurement_review`: `{inquiryId}` → exact `review`, `reviewHash`, including recipient and product/SKU/version.
- `workspace_procurement_share`: `{inquiryId, requestId, expectedRevision, expectedReviewHash, confirmed:true}` → exactly one persisted share with that merchant.
- `workspace_procurement_get`: `{inquiryId}` → owned request, actual replies and current revocation status.
- `workspace_procurement_revoke`: `{inquiryId, requestId, expectedRevision, confirmed:true}` → revoke further merchant API access. Previously read information cannot be recalled.

No buyer credential, connector or native schedule has been created during development. Production identity binding and native account authorization still require the actual account owner.

## Merchant conversation

- `GET /api/supply/inquiries`: only owned buyer requests or active shares to this exact merchant.
- `GET /api/supply/inquiries/:id`: same isolation; foreign requests return 404.
- `POST /api/supply/inquiries/:id/conversation`: `{requestId, expectedRevision, conversationId, confirmed:true}`. Bind once to this merchant's original owned conversation; persist the procurement reference as an inert message.
- `GET /api/conversations/:id/procurement`: actual associated inquiry/reply records.
- `POST /api/supply/inquiries/:id/reply`: `{requestId, expectedRevision, expectedShareHash, content, confirmed:true}`. Exact configured merchant only. Persists a real merchant reply and a reference in the bound business conversation; buyer reads it through the original MCP credential. A reply is not a binding purchase order or proof of payment.

Mutations require stable UUID request IDs, exact revisions and explicit consent. A retry with the same principal/request/scope returns its original receipt; unknown commits retain the original ID and require reconciliation. Revocation blocks subsequent merchant reads/replies. Refreshing a page cannot create another share/order.

Muse execution continues through `/api/conversations/:nativeAgentId/muse-delegations` and the existing exact-scope review/order/task/attempt/file/Session receipt protocol documented in `MUSE-CONVERSATION-API.md`. Procurement messages do not auto-dispatch Muse. Queue, notification receipt, claim, execution, returned files and human acceptance remain distinct.
