# 16 · Editorial QA

## Contract

**Input:** issue data, rendered outputs, package/runtime and evidence records. **Output:** a defect list, fixes, validation evidence and an honest release decision. **Consumer:** editor and user. Judge the complete reader journey; a green build is necessary but insufficient.

## Apply blocking gates first

| Gate | Blocking failure | Acceptable outcome |
| --- | --- | --- |
| Facts | Invented price/MOQ, source mismatch, retail presented as wholesale | Qualified source statement or explicit unknown |
| Confidentiality | Restricted/private content in any public artifact | Data removed from serialized output |
| Images | Generated scene presented as real product/factory evidence | Documentary image or clearly labelled illustration |
| Disclosure | Fictional fixture or sponsorship hidden | Adjacent, persistent disclosure |
| Usability | Required action dead, essential text clipped, unreadable data | Complete useful flow with fallbacks |
| Packaging | Tarball cannot install/run or lacks assets | Clean installation and working demo |
| Delivery report | Unrun API/client/host installation described as tested | Precise limitations and actual observations |

Do not average a blocking evidence failure into an attractive design score. Fix the underlying record and regenerate all formats.

## Review the editorial result

Read the first screen: is the category, publication date and useful angle clear? Read each product: can the buyer identify it, understand the rationale, see the purchase terms and know the most important open question? Scan the issue: do products differ meaningfully, or are they repeated promotional paragraphs?

Use `editorial-audit.mjs` for word-budget and source/unknown diagnostics. A warning is a request for judgment, not permission to rewrite facts. A short source set may justify a shorter issue. The script does not determine truth, writing quality, browser accessibility or legal image rights.

## Inspect the actual layout

Use 375, 768 and 1440 px viewports, plus 200% text zoom where possible. Inspect the full scroll length, not only the opening screenshot. Check:

- Font loading and fallback; long names and mixed-script text.
- Headline wrapping, baseline consistency and body measure.
- Product crops, aspect ratios and empty/broken-image behavior.
- Price basis, units, unknown states and source labels.
- Table headings, local horizontal scroll and page-wide overflow.
- Sponsor/demo disclosures in web, email, print and exported requests.
- Print page breaks, orphan headings and readable source references.

A screenshot is visual evidence of the captured state, not proof of every interactive state.

## Execute a realistic reader journey

1. Read the opening section without interacting.
2. Filter one category, then restore All.
3. Save two products and remove one.
4. Select three comparisons and attempt a fourth.
5. Open a source, navigate by keyboard, close with Escape and verify focus.
6. Download an inquiry and inspect its actual contents.
7. Reload and verify issue-scoped local state.
8. Disable/deny storage and confirm usable in-memory behavior.
9. Use reduced motion and inspect print.
10. Open the email without scripts and compare its claims to the web issue.

Do not send the request. A local file download is the expected end state.

## Stress the data boundaries

Use cases that change editorial meaning:

| Fixture | Expected behavior |
| --- | --- |
| All commercial terms unknown | Explicit unknowns, useful request questions, no fabricated numbers |
| One product only | No filler products or irrelevant comparison chrome |
| Long SKU and supplier names | Complete identifiers remain readable |
| Source IDs missing | Validation failure rather than invented citations |
| Private quote in a field | Excluded/blocked from all public artifacts |
| Unsafe link or injected HTML | Safe escaping/rejection, no execution |
| Generated image with product-evidence role | Reject or visibly reclassify as illustrative |
| Conflicting price/variant evidence | Qualification or unknown, no averaged price |
| Billed provider response uncertain | No automatic duplicate paid run |
| Old-format artifact | Truthful normalized issue and migration notes |

## Record results as observations

Use a short table with check, environment, result and remaining limitation. Separate unit/contract tests, clean npm installation, browser flow, visual review, live collection, live image generation and email-client testing. A provider adapter mock test verifies behavior under the mock; it does not establish account access or real API compatibility.

For editorial review, use descriptive judgments: clear / needs revision / blocking. If a numeric design score is requested, define the rubric and preserve all blocking gates independently. Never publish a fake supplier trust score.

## Gate

Deliver only after all blocking issues are resolved or clearly state that the artifact is not ready and why. Preserve the actual test report and known limitations. Stop optional retesting once the material risks and required gates are resolved; do not turn a straightforward publication into an endless checklist.
